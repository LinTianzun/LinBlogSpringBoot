## 八、方法论提炼：这次重实现是怎么"一步步"做对的

### 8.1 顺序选择的逻辑

这次的主线是：**先写问题清单 → 再写设计文档 → 再钉工具链 → 铺后端地基（配置/表结构/公共层）→ 通安全链路 → 铺业务模块 → 并行搭前端骨架 → 最后补工程化与部署**。三个关键取舍：

1. **文档先于代码，且文档之间分层**（蓝图管为什么、开发文档管怎么做、立案管现状）。这次 1497 行文档只花了一个晚上，但省掉了后面无数次"这个字段到底该是什么"的扯皮。
2. **地基先于业务**：配置强校验、22 表迁移、`common/` 公共层全部就位，才开始写第一个业务模块。`AppStartupGuard` 在 Flyway 之前跑这个设计，后面所有本地启动失败都是"配置错了"而不是"代码错了"。
3. **安全链路先于业务模块**：`JwtService` → `JwtCookieFilter` → `XsrfFilter` → `SecurityConfig` 在任何模块之前成型，业务模块只管挂权限键，不用各自实现认证。

### 8.2 可复刻的工作节奏

1. **时间戳即进度条**：整个后端 00:43 → 01:02、前端 00:50 → 01:02，是**两小时级的紧凑施工**。用文件修改时间排序就能还原依赖顺序——比读 commit log 更细，因为当时根本还没提交。
2. **配置与实现成对出现**：`AppProperties` 后面紧跟 `AppStartupGuard`；`JwtService` 后面紧跟 `JwtCookieFilter`；`package.json` 后面紧跟 `pnpm-lock.yaml`——**先定义契约，再写实现**。
3. **文档随代码走**：新文件的头注释一律注明"（§x.y）"对应开发文档的哪一节，例如 `XsrfFilter` 写"§7"、"PermissionKeys` 写"§5.2"。三个月后回头看，不用猜设计意图。
4. **契约用机器校验**：CI 的 `contract` job 用 `git diff --exit-code` 卡住 `api.d.ts` 漂移，比"记得更新类型"这种约定可靠得多。

### 8.3 踩过的坑（均据代码/配置可见）

| 坑 | 表现 | 根治方式 |
| --- | --- | --- |
| Lombok 与注解处理器 | `pom.xml` 头部直接写明"**禁用 Lombok：全部用 record 与显式代码**"，不用 `@Data`/`@Getter` | 统一用 `record`（`ApiResult`、`PageResult`、`AuthPrincipal`、`UserView` 等全是 record），少一个依赖少一类构建问题 |
| 启动强校验误伤 | 配置不全时应用起来一半才炸，或干脆带着空密码连库 | `AppStartupGuard` 以 `BeanFactoryPostProcessor` 身份在 DataSource/Flyway 之前跑，**聚合所有问题一次报完** |
| Flyway baseline 取舍 | `baseline-on-migrate` 若为 true，会把已存在的旧库"认领"成基线，掩盖真实缺失的迁移 | `application.yml` 显式 `spring.flyway.baseline-on-migrate: false`，让迁移历史是唯一事实 |
| 超管唯一性 | 应用层判断"是否已有超管"存在并发窗口 | `V1__init.sql` 用 MySQL 8 函数索引 `uk_single_super_admin ((CASE WHEN is_super_admin = 1 THEN 1 END))`，**非超管表达式为 NULL，唯一约束允许多 NULL** |
| 依赖传递断链 | MyBatis-Plus 3.5.9 起 starter 不再传递 `mybatis-spring`，运行时缺类 | `pom.xml` 显式声明 `mybatis-spring` 3.0.4 并在注释里写明原因 |
| WebP 原生库依赖 | 图片转 WebP 需要 libwebp 系统库，Windows 开发机装不上 | 选 `org.sejda.imageio:webp-imageio`，**单 jar 内捆绑 Windows x64 / macOS / Linux 原生库**，零系统级依赖 |
| JaCoCo 与 surefire | 门禁注入 agent 后测试覆盖率恒为 0，CI 直接红 | `pom.xml` 不绑 jacoco、不自定义 surefire `argLine`；JaCoCo agent **由 CI 侧命令行注入**（`jacoco:prepare-agent`），CI 注释同时提醒：日后若自定义 `argLine` 必须引用 `${argLine}` |
| openapi 导出时机 | springdoc 需要应用起来才能吐 `openapi.json` | CI 走"**先起 jar 再拉**"：`/actuator/health` 与 `/v3/api-docs` 提前在 `SecurityConfig.PUBLIC_PATHS` 里放行 |
| pnpm 版本漂移 | 不同机器装出不同依赖树 | `package.json` 声明 `packageManager: "pnpm@12.11.2"`，CI 用 `corepack enable` 锁版本，`--frozen-lockfile` 装依赖 |
| 前端 chunk 预算失控 | 打包体积悄悄增长，首屏变慢 | `.size-limit.json` 三档预算 + `vite.config.ts` 的 `manualChunks` 固定归组（echarts 单独成 chunk，禁止并入首屏 vendor） |
| 反代缓冲打断 SSE | 实时推送经 Caddy 后被攒住，事件迟迟不到 | `Caddyfile` / `Caddyfile.local` 的 `reverse_proxy` 均带 `flush_interval -1` |
| Windows 沙箱写入受限 | 自动化代理在工作区子目录写入被拒，git 写操作（add/commit）无法完成 | 提交动作交由具备权限的一方统一执行；代理侧只用只读命令（`git log`、`git status`、`Get-ChildItem`）取证 |

## 十、如果照着重做一遍：十步清单

1. **先盘点旧版的坑**，写成问题清单（哪些是补丁、哪些值得保留）；
2. **写三份分工明确的文档**：蓝图管为什么、开发文档管怎么做、进度管现状；
3. **把工具链 vendored 进工作区**（JDK + Maven），让仓库可离线复刻；
4. **先落配置与强校验**，让配置错误在启动最早期聚合报错；
5. **一次建齐表结构**，把"被逼出来的补救"（超管唯一、只存哈希、ngram 全文索引）直接写成数据库约束；
6. **通安全链路再谈业务**（JWT → 过滤器 → SecurityConfig → 权限键）；
7. **按域铺业务模块**，每个模块自带实体 / Mapper / Service / Controller 与审计埋点；
8. **前端并行推进骨架**（配置 → 契约 → 请求层 → 会话 → 路由 → 页面），数据接入等后端就绪；
9. **工程化一次到位**（CI 四 job、Compose 栈、Caddy 双配置、备份脚本），但**门禁阈值要等到真有测试时才生效**；
10. **每步都问"现在到哪、下一步是什么"**，并把未完成的部分明确标成未完成——包括文档本身。
